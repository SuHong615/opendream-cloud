# 评审门禁协议（Review Gates）

> 原则：**每个核心交付物由对应智能体独立评审，通过后才能进入下一环节。**
> 门禁不是形式：评审人必须给出证据、问题清单与明确结论；无证据 = 不通过。

## 1. 角色

| 角色 | 职责 |
| --- | --- |
| 门禁主持（Owner） | 该阶段交付物负责人；提交评审、响应问题、关闭行动项 |
| 领域评审人 | 从专业角度审查（架构/安全/产品/设计/运维/后端/能力中心） |
| `qa-reviewer` | 门禁记录唯一写入者；汇总意见、判定结论、跟踪行动项 |
| `lead` | 最终签署；PASS 后解锁下一阶段任务 |

**独立性规则**：评审人不得评审自己主写的章节；门禁主持不能给自己 PASS；`lead` 不参与具体章节撰写时可签署。

## 2. 结论定义

| 结论 | 含义 | 后续动作 |
| --- | --- | --- |
| `PASS` | 全部检查项满足，无阻塞问题 | 解锁下一阶段；记录归档 |
| `PASS-WITH-ACTIONS` | 主体验收通过，但有必须关闭的行动项 | 行动项关闭并由 qa 复核后解锁；行动项进入任务板 |
| `REJECT` | 存在范围/正确性/安全/可行性硬伤 | 打回重做；重新提交评审 |

严重级别：`P0` 阻断（必须修）、`P1` 重要（本轮修）、`P2` 建议（可排期）、`P3` 轻微（记录即可，不阻塞）。P0–P3 与门禁映射见 `docs/05-delivery/TEST-PLAN.md` §9.3；门禁判定规则见 `docs/04-reviews/README.md` §4。

## 3. 流程

```
Owner 完成交付物
  → 自检（对照本门禁 Checklist，逐项给证据）
  → 发消息给 qa-reviewer + 各评审人：路径、范围、自检结论、已知风险
  → 评审人独立阅读（只读），48h 内（本会话内尽快）给出：
       问题清单（ID/位置/级别/建议）+ 结论建议
  → qa-reviewer 汇总，写 docs/04-reviews/Gx-<topic>.md
  → lead 签署；更新 docs/00-program/STATUS.md 与任务板
  → PASS/PASS-WITH-ACTIONS 关闭后，依赖任务才可开工
```

**文件命名**：`docs/04-reviews/G<号>-<主题>.md`，例：`G1-product-definition.md`。
**一次门禁一个文件**，包含：范围、评审人、检查项逐条结论、问题清单、最终结论、签署人与时间。

## 4. 门禁清单

### G0 需求基线（Lead 主持）

- [ ] 范围 In/Out 明确，无"待定"核心项
- [ ] 每条需求有可验收标准（可测，含测量口径）
- [ ] 与上游 opencode 能力基线一致（对照 `OPENCODE-BASELINE.md`）
- [ ] NFR 可度量，且引用测试口径
- [ ] 产品差异化假设有市场依据（竞品证据支撑）
- [ ] WBS 任务有 owner、依赖、写作用域
- [ ] 风险与假设已列出，且有对策
- [ ] 团队角色与门禁规则可执行

### G1 产品定义（pm-research 主持）

- [ ] 竞品 ≥12 个，含 GitHub 链接、定位、架构、定价/许可、可借鉴点
- [ ] 结论有来源与日期；事实/推断分离
- [ ] 5 类角色画像 + 端到端旅程（含失败/异常路径）
- [ ] PRD 覆盖 E1–E10，优先级（RICE/P0-P2）合理
- [ ] 与 opencode 现有能力的差距分析一致（对照 `OPENCODE-BASELINE.md`）
- [ ] 指标（北极星/漏斗）可度量

### G2 架构（architect 主持）

- [ ] C4 上下文/容器/组件/部署四视图齐全
- [ ] `OPENCODE-BASELINE.md` §5 的 8 项待核实项 8/8 关闭，且有代码/实验证据
- [ ] 关键数据流覆盖：登录、拉起工作区、模型调用、技能安装、应用发布、MCP 调用
- [ ] 每用户 4C8G 隔离方案可证明（资源/网络/存储/身份）
- [ ] 工作区"退出不销毁、显式销毁"的状态机与回收策略明确
- [ ] 数据模型满足多租户（每表租户键/RLS 策略）
- [ ] API 契约可生成 SDK，错误码/幂等/分页/版本化规范
- [ ] 安全：STRIDE 威胁模型、密钥管理、SSRF/越权/沙箱逃逸对策
- [ ] 部署拓扑与容量模型（1,000 工作区）可推导
- [ ] ≥8 条 ADR，含备选方案与否决理由
- [ ] 失败模式与降级（模型网关故障、K8s API 故障、DB 故障）

### G3 设计（web-console 主持）

- [ ] 信息架构覆盖全部中心与角色
- [ ] 关键流程可点击走通（登录→拉起→使用→发布→分享）
- [ ] 空态/加载/错误/无权限/配额超限状态齐全
- [ ] 设计系统 tokens/组件/暗色亮色/响应式规范完整
- [ ] 无障碍 WCAG 2.1 AA 检查项
- [ ] 与 API 契约一致（字段/状态/错误码）

### G4 平台核心（platform-backend 主持）

- [ ] SSO 登录、会话、登出、越权测试通过
- [ ] API Key 生命周期与审计通过
- [ ] 模型策略下发 ≤30s 生效，未授权模型不可调用
- [ ] 工作区创建/就绪/销毁 E2E 通过，隔离测试通过
- [ ] 用量采集准确率 ≥99%（抽样对账）
- [ ] 控制台 MVP 主流程可用

### G5 能力中心（capability-centers 主持）

- [ ] Skill 发布→审核→安装→opencode 可用闭环
- [ ] 评测沙箱逃逸测试全部拦截；结果可复现
- [ ] 应用创建→构建→1C2G 部署→分享→SSO 访问闭环
- [ ] MCP 注册→绑定→调用→审计闭环；失效降级
- [ ] 四中心权限模型与租户隔离测试通过

### G6 质量与安全（qa-reviewer 主持）

- [ ] 单元/契约/E2E 覆盖率达标（核心模块 ≥70%）
- [ ] 安全扫描（SAST/DAST/镜像/依赖）无 P0/P1
- [ ] 性能压测达标（NFR 指标）
- [ ] 故障演练（Pod 杀死、DB 切换、网关超时）通过
- [ ] 成本模型与预算告警可用

### G7 部署验收（infra-devops 主持）

- [ ] Terraform plan 可复现；Helm 一键部署成功
- [ ] 灰度与回滚演练 ≤5min
- [ ] 备份恢复演练通过
- [ ] Runbook/告警/值班交接完成
- [ ] 验收报告与遗留风险清单签署

## 6. 反模式（直接判 REJECT）

- 用"后续完善"掩盖核心缺失（如没有隔离方案、没有销毁策略）。
- 需求验收标准写成"体验良好""性能优秀"等不可测描述。
- 架构图无数据流/无失败模式；API 无错误码；数据模型无租户键。
- 评审只写"同意/没问题"而无逐项证据。
- 先写代码再补设计，倒逼门禁。
- 引用竞品/数据无来源。
- 把上游 opencode 的 README 当成本项目设计。
