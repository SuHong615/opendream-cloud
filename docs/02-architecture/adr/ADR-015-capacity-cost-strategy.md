# ADR-015：容量与成本策略（默认常驻 + 可选休眠档 + 分批 100→300→1000）

- 状态：**Accepted**
- 日期：2026-11-04
- 决策者：architect / infra-devops / lead
- 关联：`ARCHITECTURE.md §9`、PLAN R3.10/NFR 成本、`deploy/DEPLOYMENT.md`

## 背景

产品红线是"退出不销毁"（D1），但 4C8G 常驻是成本主导项。1000 并发工作区 ≈ ¥64–75 万/月（不含模型）。必须在**不破坏产品承诺**的前提下，给出可运营、可解释、可分阶段投入的容量与成本模型。

## 决策

### 1) 三档运行模式（用户/组织可配，默认 A）

| 档位 | 行为 | 计算成本 | 数据 | 适用 |
| --- | --- | --- | --- | --- |
| **A. 常驻（默认）** | Pod 常驻，`ready/idle` 均占 4C8G | 100% | 全保留 | 默认；符合"退出不销毁"最强语义 |
| **B. 可选休眠档**（`idle_suspend=true`） | 闲置 N 分钟（默认 60）→ `stopped`（Pod=0），PVC 保留；下次进入从 `stopped` 启动 | 按活跃计 | 全保留（PVC） | 成本敏感团队；验收在 E3-09，默认关闭 |
| **C. 显式停止** | 用户点"停止" → Pod=0，PVC 保留 | 0（仅存储） | 全保留 | 临时不用（项目间隙、休假） |

**"退出不销毁"语义不变**：A/B/C 三档都不会删除数据；B 只是"睡了"，不是"销毁"。销毁仍是独立的显式动作（二次确认 + 冷却期 + 快照，ADR-012）。

### 2) 容量分阶段投入（不做一次性 1000 台）

| 阶段 | 并发工作区 | 节点（32C128G×7/节点×1.12） | 计算月成本（¥4,000/节点） | 触发条件 |
| --- | --- | --- | --- | --- |
| **P1 试点** | 100 | ≈17 | ≈¥6.8 万 | 内测团队（≤100 用户） |
| **P2 部门** | 300 | ≈48 | ≈¥19.2 万 | 单部门推广、SLO 达标 |
| **P3 全量** | 1,000 | ≈160 | ≈¥64 万 | 全员、容量压测通过 |
| 备选 | 1,000 | 374 × 16C64G | ≈¥74.8 万 | 故障域优先（7→3 用户/节点） |

- 扩容单位：**一次 7 个工作区 = 1 台 32C128G**；节点池 Cluster Autoscaler，扩容从 0 开始（不做固定空洞池，用 pause 占位 Pod + 抢占，见 DEPLOYMENT §9.6）。
- 每阶段必须有：压测报告（k6 + Pod 启动时延分布）+ 成本看板基线，才能进入下一阶段。

### 3) 单位经济模型（必须可解释）

**假设**（`[推断]`，需真实数据替换）：
- 注册用户 10,000，**并发率 10%** → 1,000 并发工作区（NFR 口径）。
- 活跃率（周内至少用 1 次）：60% → 6,000 WAU。
- 平均单工作区存储 20 GiB（ESSD PL1 ≈ ¥20/工作区/月）。

**成本拆分（1,000 常驻，方案 A）**：

| 项 | 月成本 | 单工作区/月 | 说明 |
| --- | --- | --- | --- |
| 计算（160 × 32C128G） | ≈¥64 万 | ≈¥640 | ¥4,000/节点假设；需按实际报价 |
| 存储（20 TiB ESSD） | ≈¥2 万 | ≈¥20 | 20 GiB × 1,000 |
| 网络（SLB/NAT/EIP/带宽） | ≈¥2 万 | ≈¥20 | 0.3–0.9 Gbps 峰值 |
| 控制面/网关/可观测 | ≈¥4 万 | ≈¥40 | 6+4+9 节点 + 托管 PG/Redis |
| **合计（不含模型）** | **≈¥72 万** | **≈¥720** | 与 infra 估算（≈¥72 万）一致 |
| 模型 token | 按用量 | 另计 | LiteLLM 计量（ADR-013） |

**关键比率（运营护栏）**：

| 指标 | 定义 | 目标/阈值 | 动作 |
| --- | --- | --- | --- |
| 常驻密度 | 并发工作区 / 已分配节点容量 | ≥ 80% | <70% 触发缩容审查 |
| 活跃率 | WAU / 总用户 | ≥ 60% | 低于则暂停扩容（买容量给不活跃用户不划算） |
| 休眠采纳率 | B 档工作区 / 可休眠工作区 | 观测（不设硬目标） | 高采纳 → 可下调下一阶段节点数 |
| 单 WAU 成本 | 月总成本 / WAU | ≤ ¥120 | 超阈值 → 成本评审 + 定价调整 |
| 模型成本占比 | 模型成本 / 总成本 | 观测，≤ 40% 预警 | 超阈值 → 模型策略收紧 / 预算下调 |
| 资源利用率 | CPU 使用 P50 / 配额 | ≥ 30% | 低于说明"占坑"；推动 B/C 档 |

**B 档（休眠）敏感性**（若 40% 工作区长期休眠）：

```
常驻需求 = 1000 × 60% = 600 → 600/7×1.12 ≈ 96 节点 → ≈¥38.4 万/月
节省 ≈ ¥25.6 万/月（-40% 计算成本），代价是唤醒时延（≤30s 目标，见 PRD-E3-09）
```

### 4) 定价/预算挂钩（不阻塞，但必须留接口）

- 计量维度：`资源时长（4C8G·小时 / 1C2G·小时）+ token`（PRD-E10-01）。
- 成本看板：按 org/user/workspace 展示"今日成本/预估月成本"，与 `usage_hourly` 同源。
- 配额：org 级月预算（USD）+ 工作区数上限；超限阻断模型调用（不阻断工作区访问）。

## 备选方案

| 方案 | 否决理由 |
| --- | --- |
| **A. 默认 scale-to-zero（休眠）** | 违背"退出不销毁"的用户预期（回来要等 30s+）；且频繁启停产生镜像/调度压力。作为 B 档可选 |
| **B. 一次性按 1000 采购** | 资本与资源浪费；无法验证 SLO 就锁死成本 |
| **C. 超卖 vCPU（requests<limits）** | 违反 4C8G 承诺（R3.1）且 QoS 降级；"独立 4C8G"是卖点 |
| **D. 自有裸金属/自建 K8s** | 运维成本与交付周期高；ACK 是既定路径 |
| **E. 按需 Serverless 容器（ECI）** | 冷启动慢（>30s 不可控）、持久 PVC 支持弱、1000 并发成本不一定低；P2 可评估作为突发层 |

## 后果

**正面**
- 成本可解释、可分阶段投入、可随活跃率调整。
- 不破坏核心产品承诺（默认常驻，休眠可选）。
- 有明确运营护栏（密度/活跃率/单 WAU 成本），避免"默默烧钱"。
- 与容量模型（ARCHITECTURE §9）一致，可交叉验证。

**负面 / 代价**
- B 档需要可靠的休眠/唤醒（PVC 重挂 + 调度 + opencode 启动），30s 唤醒需要镜像缓存与同 AZ PVC。
- 休眠会中断内存态（会话上下文需从 SQLite 恢复，见 PRD Q6），需要体验设计配合。
- 成本数字依赖报价与活跃率假设，需每月用真实账单校准；单 WAU 成本可能随使用强度上升。

## 验证

- 分阶段压测：100/300/1000 三档分别出 k6 报告 + 启动时延 P50/P95。
- 成本看板：把假设替换为真实账单后，单工作区/单 WAU 成本与本文偏差 ≤10%。
- 休眠档：40% 休眠场景下节点数降至 ≈96（±10%），唤醒 P95 ≤30s（warm node）。
- 护栏告警：密度 <70%、单 WAU 成本 >¥120 时触发。

## 计算依据

- 节点数公式：`nodes = ceil(ceil(concurrent / 7) × 1.12)`（32C128G，allocatable ≈30.5c → 7 × 4C）。
- 100：ceil(100/7)=15 → ×1.12≈17；300：43→48；1000：143→160。
- 单价假设 ¥4,000/节点/月（32C128G）、¥2,000/节点/月（16C64G）；ESSD PL1 ≈¥1/GiB/月。**均需按实际报价复核**。
